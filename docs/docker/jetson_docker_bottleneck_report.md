# 🚨 Jetson Orin NX 단독 구동 시 하드웨어·소프트웨어 버전 갈등 및 도커(Docker) 병목 분석 리포트

본 문서는 외부 GPU 서버 연동 없이 **사족보행 로봇 Unitree Go2의 내장 PC(Jetson Orin NX) 단독으로 올인원 시스템을 구축할 때 마주하는 물리적 버전 충돌 현황과 기술적 병목점**을 요약한 보고서임.

---

## 1. 🚨 우리가 마주한 삼각 버전 갈등 (현황)

로봇 단독 제어 조건 하에서 아래 세 가지 요구사항이 정면으로 충돌하고 있음.

*   **로봇 제조사 (Unitree) 고정 스택**: Go2 Pro의 모터 제어 및 보행 안정성 유지를 위해 호스트 OS는 **Ubuntu 20.04 및 ROS 2 Foxy (JetPack 5)**로 봉인되어 있음. 임의로 호스트 OS를 업그레이드할 경우 다리 모터 드라이버 커널이 깨지며 **본사 워런티가 즉시 소멸**됨.
*   **자율주행 연구진 요구사항**: 최신 AI 모델(ViNT, NoMAD 등) 및 비동기 주행 제어 프레임워크 구동을 위해 최신 환경인 **Ubuntu 24.04 및 ROS 2 Jazzy (Python 3.12 기반)** 환경이 요구됨.
*   **하드웨어 제약**: 현재 온보드 탑재된 Jetson Orin NX는 Ubuntu 20.04 기반의 **JetPack 5.1.x** 환경에 고정되어 있음.

---

## 2. 🐳 도커(Docker)를 통한 해결 공식 (이론상 대안)

호스트 OS(20.04)를 보존하면서 내부 컨테이너만 상위 버전(24.04)으로 격리 구동하는 우회로.

*   **동작 구조**: 물리 Jetson 호스트는 순정 상태인 Ubuntu 20.04 (Foxy)로 유지하고, 그 위에서 **Ubuntu 24.04 + ROS 2 Jazzy 환경의 도커 컨테이너**를 실행함.
*   **네트워크 연동**: 도커 실행 시 `--net=host` 옵션을 인가하여 네트워크 공간을 공유함. Unitree 최하단 DDS 통신은 ROS 버전에 구애받지 않으므로, 컨테이너 내부의 Jazzy 주행 알고리즘 노드가 로봇의 LIO Pose 피드백을 수신하고 `/cmd_vel` 제어 명령을 다이렉트로 로봇 모션 보드에 주입할 수 있음.

---

## 3. ⚠️ 하지만 도커가 쉽게 풀리지 않는 진짜 이유 (치명적 병목점)

일반 x86 데스크톱 환경과 달리, GPU 드라이버가 Tegra L4T 커널에 특수 매핑된 **Jetson 임베디드 보드에서는 다음과 같은 하드웨어 종속성 장벽에 가로막힘.**

### ① 엔비디아 가속(L4T) 및 CUDA 드라이버 버전 미스매치 (가장 치명적)
*   **커널 종속성**: Jetson의 GPU 드라이버는 호스트의 L4T(Linux for Tegra) 커널 버전과 물리적으로 묶여 있음. 호스트가 JetPack 5(Ubuntu 20.04)이면 CUDA 드라이버 스택은 11.x 스택에 강제 제한됨.
*   **라이브러리 충돌**: 이 상태에서 컨테이너 내부만 무작정 Ubuntu 24.04 이미지로 올리면 최신 CUDA 12.x/13.x 툴킷이 설치됨. 이 상태로 GPU 가속 옵션(`--runtime=nvidia`)을 활성화하여 도커를 실행하면 **호스트의 낮은 드라이버와 컨테이너 내부의 높은 라이브러리가 불일치하여 `Driver/library version mismatch` 에러와 함께 GPU 연산이 완전히 마비**됨.
*   **영향**: GPU 가속이 불가능해지면 ViNT/NoMAD 모델 추론을 CPU로만 처리해야 하므로, 루프 지연으로 인해 로봇의 실시간 동적 제어가 원천 불가능해짐.

### ② ARM64(aarch64) CPU 아키텍처 충돌
*   일반적인 ROS 2 Jazzy 공식 도커 이미지(`osrf/ros:jazzy-desktop`) 등은 대부분 일반 PC용 x86_64 기반으로 빌드되어 있어, Jetson Orin NX(ARM64) 환경에서 구동 시 `Exec format error`가 발생하며 시작 직후 크래시가 남.

### ③ 센서 장치 디바이스(/dev) 접근 권한 누락
*   컨테이너 가상 격리 공간 내부에서 로봇 내장 L1 라이다나 추가 장착한 D435i 카메라의 USB/시리얼 포트에 접근하려면 `--device` 마운트 및 udev 권한 세팅을 수동 매핑해야 하며, 세팅이 미세하게 불일치할 경우 센서 드라이버 노드가 장치를 찾지 못하고 뻗게 됨.

## 💡 4. 월요일 미팅 시 제시 가능한 우회/대안 전략

버전 미스매치 장벽을 극복하기 위해 기술적으로 취할 수 있는 세부 제안 전략들임.

*   **대안 A: NVIDIA 공식 L4T 베이스 이미지 상에서 ROS 2 Jazzy 소스 빌드 (정공법)**
    *   NVIDIA가 JetPack 5 버전과 호환성을 보장하도록 제공하는 L4T 베이스 이미지(`nvcr.io/nvidia/l4t-base`) 위에, ROS 2 Jazzy 소스코드를 올려 직접 gcc로 수동 컴파일(Source Build)하여 커스텀 도커 이미지 스택을 새로 빌드함. (단, 컴파일 시간이 매우 길고 의존성 패키지 매칭 난이도가 극상임.)
*   **대안 B: ROS 2 Jazzy 탑재 포기 및 Pure Python + ONNX Runtime 연동 (현실적 추천)**
    *   최근 팀원들(현서, 건민)의 대화 내용에 따르면, EKF 오도메트리 융합을 ROS 의존성 없이 **Pure Python (NumPy/SciPy)**으로 직접 구현하기로 가닥을 잡았고, 모델 출력 역시 **ONNX 포맷**으로 추출이 끝난 상태임.
    *   따라서 굳이 젯슨 컨테이너 내부에 무거운 ROS 2 Jazzy를 올릴 필요 없이, **JetPack 5와 완벽히 호환되는 공식 CUDA 11.x 지원 파이썬 도커 환경**을 올린 뒤 **ONNX Runtime(GPU 가속 지원) + Pure Python**만으로 제어 파이프라인을 가볍게 구동하는 방식을 강력하게 추천함.
