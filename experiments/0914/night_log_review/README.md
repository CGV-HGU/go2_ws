2026-09-14 Jetson에서 수행한 파일 기반 분석이다. 로봇 주행 코드·속도·시간제한·네트워크 설정은 변경하지 않았고 Git 커밋/푸시는 하지 않았다.

### 두 번째 회차: 위치 발신 중단보다는 제어기 수신·처리 지연 의심

00:54:20.45에 관측 회전이 `LOCALIZED_POSE_STALE`로 끝났다. 요청 회전량은 약 -58.72°, 측정량은 약 -59.18°였다. 회전 각도에 못 도달해서 난 `MOTION_TIMEOUT`이 아니다.

제어기는 마지막으로 받아들인 `/s2e/odometry/pose`의 시각이 0.5초 범위를 벗어나면 전체 주행을 억제한다. 이 이름의 `LOCALIZED`는 이 회차에서 ICP 정합을 의미하지 않는다. `pose_source=odometry`, `icp_corrections_used=false`다.

정지 시각을 기준으로 독립 기록기가 받은 최신 control pose는 약 0.135초 전 데이터였고, 최신 odom은 약 0.081초 전 데이터였다. adapter 상태도 READY였으며 위치 점프 기록은 없다. 반면 제어기의 동작 로그에서 사용한 odom은 약 0.303초 전 값이었다. **새 데이터가 기록기까지 오는 경로와 제어기가 처리하는 경로의 지연이 달랐다는 단서**다.

코드에서 센서 콜백과 주기 제어 콜백은 기본 콜백 그룹을 공유하고, 주기 제어 중 동기 Sport 통신을 수행한다. 처리 대기나 수신 지연이 후보 원인이다. 그러나 오류 순간 제어기가 보유한 pose stamp, 콜백 시작/종료 시각, 스케줄링 지연은 기록되지 않았다. 정확한 병목을 확정했다고 보고하지 않는다. 단순히 freshness 제한을 늘리는 수정도 아직 하지 않았다.

## 학교 와이파이뿐 아니라 핫스팟도 끊긴 이유

학교 Wi-Fi와 핫스팟은 Jetson의 같은 USB 무선 장치/드라이버를 사용한다. 00:50:45 장치 재인식 로그에 `Realtek 802.11ax WLAN Adapter`, USB ID `0bda:b831`가 명시되어 있다. 00:00~01:04 범위에 `usb 1-2` 연결 해제 기록이 23건 있다. 00:50:44, 01:00:26 이후에도 장치 재인식·리셋이 반복됐다.

작업자는 이번 검토에서 **연결 복구를 위해 동글을 뺐다가 다시 꽂은 적이 있다고 확인했다.** 따라서 이 23건을 자동 USB 장애 23회로 세거나 동글 결함의 증거로 단정하면 안 된다. 정확한 수동 재연결 시각은 미기록이다. 별도로 `Ultra`의 링크 해제와 `ssid-not-found` 실패는 직접 확인되므로 학교 AP만의 문제는 아니었다. 핫스팟 신호/절전, 무선 드라이버, USB 접촉/전원, VPN/서버 경로 중 최초 원인은 아직 분리되지 않았다. `reason=0`, `ssid-not-found`만으로 휴대전화나 드라이버 하나를 지목할 수 없다.

현재 조회 시 Wi-Fi 절전은 켜져 있으나 해당 USB 장치의 runtime autosuspend는 꺼져 있다(`power/control=on`, delay=-1000). “USB 자동 절전이 원인”이라고 단정할 근거도 없다. 이번 검토에서는 설정을 바꾸지 않았다.

로봇 센서와 Sport 제어는 유선 Go2 링크, 원격 VLM은 외부 인터넷/VPN 경로다. Wi-Fi 단절이 VLM을 막는 것과 제어기의 pose freshness 오류는 다른 경로다. 두 번째 회차는 VLM 오류가 0건이었고, 그 오류 시각에 무선 단절을 원인으로 확정할 자료가 없다.

## Direct PixelNav는 왜 실패했는가

| 회차 | 종료 시간 | 최종 잔여거리 | 10Hz 경로 추정 | 모델 출력 횟수 |
|---|---:|---:|---:|---:|
| 4-002 | 35.40초 | 7.46m | 4.91m | 21 |
| 4-003 | 59.34초 | 5.66m | 7.06m | 31 |
| 4-004 | 70.54초 | 9.35m | 6.01m | 29 |
| 4-005 | 58.90초 | 8.79m | 3.73m | 21 |
| 4-006 | 27.48초 | 9.47m | 3.73m | 16 |

다섯 회차 모두 마지막 raw/effective logits가 동일하고 argmax가 STOP이며 `stop_source=model`이다. 360초 제한, 500 step 제한, 32 history 초과 강제 정지, 미지원 look 차단으로 종료된 것이 아니다. Direct 모드의 VLM 호출은 0건이므로 VLM 인터넷 장애도 이 조기 STOP의 직접 원인이 아니다.

실제 초기 RGB와 네트워크에 입력된 224×224 목표 영상을 확인했다. **투영된 목표 마스크가 보이는 벽 부근에 겹쳐 있다.** 뒤쪽 실제 목표 좌표를 앞 RGB 평면에 투영해도 가려진 목표가 새로 보이게 되는 것은 아니다. 현재 Direct 입력은 고정된 첫 목표 이미지/마스크와 영상 이력이며, 최종 11.30m 좌표 자체를 매 단계 네트워크에 거리로 넣는 구조는 아니다.

종료 영상의 모델 목표 예측은 벽·기둥·의자 근처 등으로 달라졌다. 이 증거는 **가려진 최종 목표를 단일 영상 목표로 주었을 때의 시각 목표 추적/해석 한계**와 부합한다. 다만 어떤 특징 때문에 STOP logits가 높아졌는지, 학습·반사 바닥·룩 전진 대체 각각의 기여까지 분리한 실험은 아니다. “PixelNav 학습 자체가 잘못됐다”거나 “모델이 정확히 1m 도착을 판단했다”고 결론 내리지 않는다. 모델의 `distance_prediction` 단위도 검증되지 않아 미터로 쓰지 않았다.

이 비교군은 **Direct-goal PixelNav + 동일한 Go2 동작 어댑터(look→20cm)**라고 명시해야 한다. 카메라 look 동작까지 원본 그대로 실행한 PixelNav로 표기하면 안 된다.

## 정량분석에 사용할 수 있는가

**사용할 수 있는 실제 주행 데이터다. 다만 현재 자동 종료 기록을 그대로 최종 논문 SR/SPL 표로 바꾸는 것은 아직 부정확하다.** 추가 로그 수집 없이 지금 가능한 것은 다음과 같다.

최근 Full 4-002/4-003의 기존 기록 검사는 `sweep_scheduler_trace.jsonl` 부재를 지적했다. 두 회차 모두 위치·오도메트리·정책 출력·명령·원시 센서 기록은 존재한다. 스케줄러 trace는 해당 조정 이벤트가 발생할 때 파일을 생성하는 구조이므로, 파일 부재만으로 전체 Pose 로그 손실이나 비동기 비활성화를 단정하지 않는다. 반대로 완전한 스케줄러 감사 기록이 있다고 주장하지도 않는다. 이번 `validation.json`의 PASS는 **내보낸 파일과 계산의 대조 결과**이며, 기존 회차의 `recording-integrity.json` 실패를 덮어쓴 것이 아니다.

1. 에피소드별 자동 거리 도달 여부, 종료 원인, 시간, 상대 오도메트리 경로, 동작 수, look 빈도, VLM 호출 수·지연·실패율을 보고한다. `trajectory.csv`에는 XY뿐 아니라 yaw와 시각이 포함되어 Pose logging을 재확인할 수 있다.
2. Direct 4-002는 작업자가 개입·접촉·진로 방해가 모두 없었다고 확인한 조기 STOP 실패다. 마지막 Ours 4-003은 개입한 회차로 표시한다. 다른 회차의 `0` 하나/미입력을 자동으로 “세 항목 모두 없음”으로 해석하지 않는다.
3. 같은 look 20cm·회전 0.8 조건의 4번 기록을 모두 보존하면, Ours는 자동 거리 도달 1/3, Direct는 0/5다. **이 숫자는 자동 종료 결과의 기술통계이며, 확정 논문 SR이나 통계적 우월성 주장이 아니다.** Ours에는 네트워크·제어기 실패와 수동 이동이 포함되고, 같은 물리 시작점의 오차와 현장 진술도 완전히 확인되지 않았다. 성공 회차만 골라 Ours 100%로 보고하면 안 된다.
4. 정책 자체 비교와 실제 시스템 전체 성능을 구분한다. 시스템 성능 집계에서는 네트워크 장애/작업자 개입도 사전에 정한 규칙에 따라 실패로 남긴다. 정책 비교에서 통신 장애를 제외하려면 양 방법에 공통으로 적용할 객관적 기준을 먼저 정하고 제외 건수도 공개한다. Direct가 네트워크를 쓰지 않는 점도 비교 조건이다.

SPL은 `S × L / max(P,L)`이며 `L`은 장애물을 고려한 최단 경로다. 벽을 통과하는 시작–목표 직선거리나 매핑 때 걸은 전체 경로를 `L`로 쓰면 안 된다. 현재 각 시작/목표에 연결된 검토 완료 최단 경로 참조가 없고, 일부 성공의 물리 도착 확인이 미완료라 최종 `paper_spl`을 비워 두었다. 수동 이동이 포함된 마지막 회차의 63.43m도 `P`에 쓰지 않는다. 실패를 0으로 표시할 수 있더라도 성공 회차까지 포함한 전체 SPL이 자동으로 확정되는 것은 아니다. [평가 지표 원문](https://arxiv.org/pdf/1807.06757).

현재 프로토콜은 **오도메트리 추정거리 1m 이내 자동 종료, 최종 yaw 미평가**다. 위 원문이 권고하는 DONE 액션/최단 경로 거리 기준과 차이가 있으므로 “그대로의 표준 벤치마크”라 하지 않고 실로봇 평가 프로토콜을 명시한다. 이 차이를 알리지 않고 기존 숫자를 공식 SR/SPL로 부르는 것을 피한다. [평가 권고](https://arxiv.org/pdf/1807.06757).

기존 `experiments/0913/benchmark_metrics.json`의 6회 결과는 앞서 수행한 별도 작은 지도·두 목표 실험이다. 이번 다섯 목표/야간 비교에 합치지 않았다. 그 파일에 사용된 직선거리 SPL 표기를 이번 최단 경로 참조로 재사용하지도 않았다. 기존 파일은 보존했다.

## 다음 수정·검증 우선순위

1. `Ultra` 링크 실패와 수동 USB 재연결을 분리해서 원인을 확인한다. 다음 연결 유지 검사에서는 동글을 건드리지 않은 구간을 명시하고, 휴대전화 핫스팟·외부 인터넷·VLM/VPN 경로를 함께 기록해 어디부터 끊기는지 확인한다. USB 장치 자체의 자동 해제는 이 구간에서 재발할 때 별도로 조사한다. 네트워크를 안정화하지 않고 같은 Full 장거리 주행만 반복하면 다시 서버 대기에 막힐 수 있다.
2. 제어기 freshness 오류 순간에 내부 pose/odom stamp와 콜백·Sport 왕복 지연을 남겨 병목을 특정한다. 센서 수신이 동기 제어 통신 때문에 밀리는지 재현하고 수신/처리를 개선한다. 센서 검사를 끄는 방향으로 해결하지 않는다.
3. 연결이 끊긴 뒤 30초 호출을 여러 단계에서 재시도하며 긴 대기가 생기는 정책을 검토한다. 비동기 실행 중 준비된 결정을 쓰는 구간과 큐가 비어 기다리는 구간을 각각 측정해야 한다. HTTP 지연 합을 정지 시간으로 대체하지 않는다.
4. 논문 실험 전 Ours/Direct 공통 전체 제한을 합의한다. 이번 실행은 **모두 해당 파일에 기록된 360초 조건**으로 보존한다. 연구원이 언급한 시뮬레이터 1800초는 별도 후속 설정 검토이며, 이번 결과를 1800초 성공으로 소급 변경할 수 없다. 가까이 갔던 long5 5-001도 1.513m 남은 시간초과다.

## 재현과 보존

`export_review.py`는 원본 이벤트를 읽고 기존 `robot_episode_archive.py` 방식으로 지표를 재계산한다. 경로는 목표 발송~최초 직접 정지 요청의 오도메트리 XY를 고정 시각 간격으로 보간한 추정치이며 5/10/20Hz 민감도를 함께 남긴다. 정지 이후 관성 이동은 이 경로 길이에 포함되지 않는다. `network_evidence.py`는 기존 시스템 로그를 발췌하고, `make_review_figures.py`는 표·그림을 만든다. `finalize_review.py`는 보완된 현장 진술을 반영하고 해시·지표·입력 일치 검사를 수행한다.

코드 재실행은 동일 출력 디렉터리의 파생물을 갱신하므로 제출용 결과를 고정한 뒤에는 새 디렉터리에서 재현한다. 원본 위치/DB/rosbag에는 쓰지 않는다. 전체 원본 해시를 다시 읽어 검사한 것은 아니며, 이번에 내보낸 파일은 압축 해제 결과와 원본의 SHA-256을 대조한다. 검사 범위는 [validation.json](validation.json)에 명시했다.

다른 컴퓨터에서도 `make_review_figures.py`는 내보낸 CSV 파생 데이터와 선택한 NPZ를 사용해 비교 그림을 다시 만들 수 있다. 원본 전체를 요구하는 `export_review.py`/`finalize_review.py`와 구분한다. 배포받은 묶음 자체는 이 디렉터리에서 `sha256sum -c SHA256SUMS`로 확인할 수 있다. 전체 지표 재생성 순서는 export → network → figures → finalize이며, 수정한 코드로 다시 생성한 결과를 기존 제출본과 혼합하지 않는다.
