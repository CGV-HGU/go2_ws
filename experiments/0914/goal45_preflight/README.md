# 4번 재현·새 5번 좌표·재매핑·실주행 전 검증

2026-09-14 Jetson 작업. **기존 지도 재사용이 우선이며, 재매핑을 지금 시작할 근거는 없다.** 현재 주행은 표시 시작점에서 재앵커하는 오도메트리 방식이다. 지도 파일 손상·목표 번호 혼동·좌표 변환 오류는 이번 검사에서 발견되지 않았다. 지도 전역 정합이나 물리적 좌표 정확도까지 검증됐다는 뜻은 아니다.

회전 완료 판정과 센서 처리 경합을 개선하는 **격리된 수정 후보와 Docker 이미지**도 만들었다. 247개 제어 경계 검사를 통과했으나 **현재 캠페인·실행기에는 활성화하지 않았다.** 기존 `~/run_goal.sh`는 여전히 `8a36ebd…` 이미지를 사용한다. 원본 지도·목표·주행 기록·실행 대기 회차는 변경하지 않았다. 로봇 명령은 0건이다.

## 1. 어제 PixelNav 4번의 짧은 평가

Direct-goal PixelNav로 4번을 실제 주행한 5회는 **기록상 도착 0/5**, 평균 실행 **50.33초**, 평균 최종 목표 거리 **8.15m**였다. 모두 시간초과나 look 차단 전에 모델이 STOP을 선택했다. 118개 정책 행동은 기존 원본 구현 재생에서도 같았다.

가려진 최종 목표를 초기 영상의 픽셀로 투영한 조건에서 최종 목적지까지 연결하지 못한 사례다. 정책 자체의 일반적인 학습 결함으로 단정하지 않는다. look은 20cm 전진으로 대체했으며, 현장 무개입·무접촉·무방해 확인은 002 한 회차만 있다. [회차별 수치와 정량 사용 범위](../pixnav_quantitative_evaluation/README.md).

## 2. Ours 4번의 성공 기록과 현재 좌표

`original5/full-goal-4-009`는 **302.35초, 잔여 거리 0.98396m에서 GOAL_DISTANCE_REACHED**로 끝났다. 추정 경로는 14.97m이고 pose·동작·모델 기록이 있으며 당시 기록 무결성 검사는 통과했다. 현장 도착·개입 상태는 별도 확인이 남아 있어 로그 기반 도착과 논문용 확정 성공을 구분한다.

그 뒤 4번 실패는 다른 원인이었다. `recaptured5/4-002`는 124초의 `LOCALIZED_POSE_STALE`, `4-003`은 네트워크 요청 25건 중 오류 14건 이후 사용자 수동 이동이 확인된 회차다. 마지막 회차의 약 63m 궤적을 자율 주행 경로로 쓰지 않는다. 속도·이미지가 다른 더 이른 4번 회차에는 회전 시간초과도 있었다.

**현재 목표 1~4번의 fixed-start XY는 4번 성공 캠페인과 모두 정확히 같다.** 현재 4번 값은 다음과 같다.

| 목표 | 시작점 기준 X (전방) | Y (좌측 양수) | 직선거리 | 초기 전방에서의 방위 |
|---|---:|---:|---:|---:|
| 4 | +10.613861m | −3.886406m | 11.303017m | 오른쪽 20.111° |
| 5 | +14.443445m | −6.559551m | 15.863191m | 오른쪽 24.425° |

이는 길을 따라가는 경로 길이나 ‘처음에 이 각도로 돌고 직진하라’는 제어 명령이 아니다. 저장 yaw는 4번 −0.63538rad, 5번 −1.64127rad이지만 최종 yaw를 제어·평가하는 조건은 아니다. 도착은 직선거리 1m 반경이다.

## 3. 5번 좌표와 지도 확인

- 현재 5번을 원래 캡처의 origin·센서 snapshot으로 `capture_goal()`에 다시 넣어 **같은 XY가 정확히 재생성됨**을 확인했다. 임의 보정·옛 5번 재사용은 없었다.
- 실제 `goal_in_odometry()`를 서로 다른 시작 위치·방향 6개에 적용했다. 4·5번 총 12개 왕복 변환 오차는 1e-12m 미만이었다.
- 지도 표시 파일의 목표 계획 해시, 지도 해시, 원점·방향 변환이 현재 캠페인과 일치했다. 지도 오버레이에서 4번은 `(10.953683, −3.256439)m`, 5번은 `(14.963043, −5.651527)m`다. **이 지도 좌표를 fixed-start 좌표 대신 주입하면 안 된다.**
- 원본 지도 DB SHA-256은 `38348c5458ce632851c628f53a51f3fee40cf1678e5fb982361bd1f50fb16ad9`로 그대로이고, 읽기 전용 SQLite quick_check는 `ok`다. Node 365개, Link 행 904개가 있다. 이것이 루프 폐합 904회라는 뜻은 아니다.
- `ground_truth_pose` 필드에는 365개 blob이 있지만 모두 12개 float가 0으로 채워져 있었다. **외부 Ground Truth 좌표가 들어 있다고 해석할 수 없다.**
- cached optimized pose로 투영된 원본 셀 지도에서 4·5번 중심 셀은 모두 free였다. 반경 1m의 셀 집계는 4번 free 851/unknown 412, 5번 free 1,252/unknown 4였다. 해당 원 안에서 occupied 셀은 없었다. 이는 그림의 정적 셀 검사이며 실제 장애물·통행 가능 최단 경로·실측 도착을 보증하지 않는다. 주행 차단 조건으로 추가하지 않았다.

[원래 지도와 새 5번 표시](../../../2dmap/0914/2d_goals_map_recaptured5.png), [현재 파일·변환·준비 회차 검사 결과](goal45_audit.json).

남은 불확실성은 **물리적 좌표 정합**이다. 새 5번을 찍고 같은 시작점으로 돌아왔다고 보고한 시점에 오도메트리는 0.468m·5.43° 차이를 기록했다. 실제 재배치 차이와 누적 drift를 구분할 외부 측정은 없다. 시작 방향만 1° 다르면 15.86m 목표의 횡방향 차이는 약 0.277m, 3°면 약 0.830m다. 당시 실제 목표 오차가 꼭 이 값이었다는 뜻은 아니다. 이 때문에 폐합 잔차를 그대로 빼서 5번 좌표를 임의 수정하지 않았다.

### 재매핑을 해야 하는 경우

현재 목표를 같은 표시 시작점에서 재현하는 데 재매핑은 선행 조건이 아니다. 먼저 시작 위치·방향을 재현하고 5번의 실제 바닥 위치를 확인하는 편이 낫다. 시작 마커가 없어졌거나 기존 좌표계와 물리적 대응을 복원할 수 없으면 origin·목표를 새 세트로 다시 캡처해야 한다. 이것도 반드시 지도 전체를 다시 만드는 일과 같지는 않다.

자유로운 시작점에서 ICP 전역 보정으로 주행하려 하거나, 지도 형태가 실제 공간과 달라 SPL용 경로 기준을 만들 수 없다면 지도·localization을 별도로 검증하고 필요 시 재매핑해야 한다. 지금의 DB 무결성 검사로 지도 모양 전체나 전역 localization 성능이 검증된 것은 아니다. 재매핑만으로 회전 완료 판정이나 명령 통신 경합이 해결되지는 않는다.

## 4. 제어 수정 후보의 새 검증

후보 이미지: `sha256:2fc034b16066c3e0aaf170d164825903fbfc1f48122ced32411c616868428d40`.
태그: `escape-navigation:goal45-sensor-candidate-20260914`. 현재 캠페인 이미지와 구분하여 보관했다.

### 센서 처리

센서 콜백과 잠금을 명령 전송 경로에서 분리했다. 센서 수신에서 동작 완료 결과를 직접 발행하던 처리는 제어 타이머로 넘겼다. 제어·STOP·세대 교체는 기존 제어 잠금 아래 순서를 유지한다. 잘못된 odom은 보류 오류로 기록하고 다음 제어 tick에서 이동 전에 차단한다. 제어 tick은 사용할 센서 샘플을 먼저 확보한 뒤 시각을 읽어, 병렬 수신으로 ‘미래에 수신된 샘플’ 오류를 만들지 않게 했다.

실제 ROS 콜백, 30Hz 합성 센서, 3개 executor thread, 기록용 가짜 Sport로 시험했다.

| 명령 응답 지연 | 8초 동안 move 호출 | 최대 pose age | 결과 |
|---|---:|---:|---|
| 80ms | 93 | 42.0ms | stale 없음 |
| 95ms | 79 | 42.9ms | stale 없음 |
| 95ms 반복 | 79 | 42.5ms | stale 없음 |
| 150ms | 52 | 41.9ms | stale 없음 |

150ms는 실제 transport의 100ms timeout보다 긴 **콜백 경합 시험**이다. 실제 Sport가 150ms를 허용하도록 바꾸었다는 뜻이 아니다. 가짜 매크로가 계속 전진 출력을 내는 조건이며 실제 GPU/VLM·명령 수신 전체 부하나 실제 Go2 펌웨어를 검증한 것은 아니다. 정지 요청은 진행 중인 동기 통신이 끝난 뒤 처리되므로 transport의 시간 제한·watchdog은 계속 필요하다.

### 회전 완료

각도 흔들림 허용폭을 명시적인 `rotate_settle_spread_deg` 설정으로 만들었다. 기본값은 기존 0.25°이며 후보 비교에서만 1°를 사용했다. 원래 3° 목표 허용각, 정지 각속도 0.1rad/s, 0.35초 관측 구간을 유지한 후보는 이전 5번의 405개 각도 기록 재생에서 약 **11.94초에 OK**가 됐다. 기존은 **20.30초에 MOTION_TIMEOUT**이었다.

0.15rad/s까지 정지 각속도를 바꾼 비교는 2.83초에 OK였지만 이 값을 활성화하지 않았다. 기록되지 않은 실행기 내부 선속도를 0으로 가정한 각도 재생이므로 실제 정지 여부·그 뒤 자세를 보증하지 않는다. 선속도 0.08m/s를 넣었을 때는 계속 완료를 거절했다.

### 회귀·결함 주입 결과

**247개 통과.** 제어 경계, 지연된 pose 결과, sweep 소유권, 늦은 동작, 정지·취소, recoil, 짧은 전진, 회전 정지 예산과 새 센서 잠금·잘못된 odom·진행 중 Move 이후 STOP 순서 검사를 포함한다. 별도의 4회 ROS 지연 시험과 405개 각도 재생을 이 숫자에 더하지 않는다.

첫 검사에서 기존 두 사례는 센서 콜백 안에서 즉시 결과가 발행된다고 가정해 실패했다. 후보용 검사 복사본에서 제어 tick을 진행한 뒤 동일한 causal pose·sweep 조건을 확인하도록 바꿨다. 다음 검사 한 사례는 ROS 메시지의 기본 quaternion이 정상 w=1인데도 0이라고 가정한 fixture 오류였고, 명시적으로 w=0을 넣어 수정했다. 초기 실패 로그도 보존했다. 기존 runtime 테스트 파일은 수정하지 않았다.

후보 이미지를 실제로 빌드하고 설치된 세 파일의 해시와 새 파라미터 전달을 검사했다. 초기 Docker 빌드는 image ID가 레지스트리 이름으로 해석되어 실패했고, 동일 로컬 이미지에 별도 태그를 붙여 빌드했다. 원격 기반 이미지를 교체한 것은 아니다.

자료: [후보 patch](candidate.patch), [센서 지연](sensor_candidate.json), [회전 재생](settling_replay.json), [247개 결과](candidate-final-tests.log), [이미지 검증](candidate_image_validation.json). **현재 실행기에는 이 후보가 적용되지 않았으므로 현재 4번 재시도의 실패 문제가 해결됐다고 보고하지 않는다.**

## 5. 기록·실행·네트워크 확인

현재 준비된 Full 4·5번과 Direct 4·5번, 총 4개 회차의 이미지 존재, 설정·파일 해시, 목표 바인딩, 실행 인자·정지 및 기록 제한, 셸 문법 검사가 통과했다. 검사기의 마지막 manifest 쓰기는 메모리 복사본에서 억제해 기존 회차를 보존했다. 이는 현재 이전 이미지의 준비 파일이 일관된다는 뜻이지 알려진 결함이 없다는 뜻은 아니다.

설정은 Full 비동기, 일반 전진 25cm, look 20cm 전진 대체, 속도 상한 0.5m/s·0.8rad/s, 도착 반경 1m, 전체 1800초다. pose·정책 입출력·센서 기록과 종료 시 보관 경로가 연결돼 있다. 실제 센서 수신·기록 파일 완결성은 본체 부팅 후 및 회차 종료 후 확인해야 한다.

현재 모델 목록 조회 3회는 HTTP 200, 약 49~100ms이며 `qwen3.5-9b-instruct`가 올라와 있었다. 이는 모델 목록 조회 시간이다. 실제 영상 VLM 추론 지연이나 실험 장소 Wi-Fi의 안정성을 의미하지 않는다. [조회 결과](network_models.json).

**저장공간은 제한 요인이다.** 검사 당시 약 65.8GiB가 남았고, 실행기가 1800초 한 회차에 요구하는 공간은 약 62.7GiB다. 현재 한 회차 공간 검사는 통과하지만 4번을 수행한 뒤 5번 준비 시 이 검사를 통과하지 못할 수 있다. 30MiB/s 상한과 공통 10GiB 예비 공간을 가정하면 두 회차 최악 조건은 약 **115.5GiB**다. 현재 원본 기록 방식 그대로 두 회차를 보장할 수 없다.

원본 로그 삭제·시간 제한 축소는 하지 않았다. 후속 작업에서는 검증된 외부 보관 공간을 확보하거나, pose·명령·모델 실제 입력·결과 증거를 보존하는 경량 기록 조건을 정해야 한다. [기존 용량 분석·정리 후보](../storage_review/README.md).

Ours 2번에서 확인한 목표 근처 STOP→탈출 후보 문제도 별도 로직 과제로 남아 있다. 현재 후보는 그 VLM/복구 정책이나 look 처리 방식을 바꾸지 않는다. [실패 후속 분석](../pixnav_failure_followup/README.md).

**이번에 ‘실로봇만 켜면 모든 검증이 끝났다’고 결론 내리지는 않는다.** 재매핑을 먼저 하기보다 현재 성공했던 좌표를 유지하고, 공통 제어 후보의 적용과 기록 공간을 마무리하는 순서가 타당하다.
